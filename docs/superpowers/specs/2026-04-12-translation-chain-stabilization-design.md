# Translation Chain Stabilization Design

## 目标

本设计用于收敛当前 `A -> B -> C0 -> 装配层 -> D -> 后置审校` 链路中，已经确认存在的两类核心问题：

1. Agent A 的 `globalConstraints` 仍可能产出错误的全局“不译”硬约束，并继续污染下游。
2. 当前名称治理链路虽有 `confirmedTerms` 顺序传播，但缺少稳定实体锚点、alias 归一能力与正文合规校验。

本设计同时考虑后续将接入一个较为自治、类似 Codex 工作模式的审校/精修 agent，因此要求主链先做到：

- 尽量不输出明显脏稿
- 显式暴露问题
- 支持链路内修订
- 为后置 agent 提供稳定知识锚点

## 设计边界

本设计必须遵守以下边界：

- 不重做 Agent A / B
- 不回退到大 orchestrator
- 不让装配层承担项目级实体治理职责
- 不让 D 承担主检索职责
- 不把 loop 临时状态塞回稳定执行契约
- 不用静默 fallback 掩盖问题

## 非目标

本次设计明确不是：

- 重写 A / B 的核心职责
- 移除现有 `bookAnalysis / globalRisks / translationStrategyNotes / globalConstraints`
- 移除现有 `entities / backgroundQuestions / translationRisks / keyExpressions / personAliasHints`
- 移除现有 C0 外部知识检索与知识卡沉淀链路
- 移除现有 D 的两轮翻译与修订机制
- 让未来后置审校 agent 接管基础清污职责

原则是：**只增不砍，先挂接、后替换，默认兼容现有链路。**

## 现状判断

基于当前代码与最新 `book-1` 全链路冒烟，当前真实现状如下：

1. Agent A 的 prompt 已加入 `globalConstraints` 边界提醒，但执行层没有第二道筛选。
2. `BookAnalysisLlmResultNormalizer` / `BookAnalysisLlmResultParser` 仍会把错误全局约束近似原样放入 `GlobalConstraint`。
3. 这些错误约束会继续传入：
   - `ChunkSegmentationPromptRenderer`
   - `ChunkAnnotationPromptRenderer`
   - `TranslationTaskInputAssembler`
   - `TranslationPromptRenderer`
4. D 侧虽然已引入部分 `targetLanguage` 约束，但仍会消费上游污染过的 `activeConstraints`。
5. D 当前执行层 validator 主要识别正文边界污染，还没有“目标语言正文纯度”与“active glossary 正文合规”校验。
6. 当前名称治理链路存在传播机制，但缺少实体归一、正文合规校验与可靠首现命名兜底。

因此，当前不能把“D/C0 局部已接入 `targetLanguage`”误判为“整条链路的目标语言约束已经收稳”。

## 一、Agent A 的 `globalConstraints` 边界治理

### 1.1 设计目标

将 `globalConstraints` 收紧为真正的“全书级、长期稳定、可跨 chunk 复用”的原则集合，禁止实体级不译策略继续冒充全局硬约束进入下游。

### 1.2 允许进入 `globalConstraints` 的内容

只允许以下类型：

- 命名治理总原则
- 风格/语体边界
- 格式与排版原则
- 目标语言总原则

典型例子：

- 全书命名应保持一致
- 正文默认使用目标语言
- 避免解释性增译
- 时间、地址、标题等格式处理应前后一致

### 1.3 禁止进入 `globalConstraints` 的内容

以下内容一律视为非法：

- 单个或少量实体的具体译法/不译法
- “所有专有名词保持原文不译”
- “所有引述文本保持原文”
- “首次出现加括注，后续只保留原文”
- 单本书名、单个人名、单个地名、单个称呼的硬编码策略
- 局部命名判断、局部候选译法、局部风险提示

这些内容应分别落到：

- `globalRisks`
- `translationStrategyNotes`
- 后续的内生知识卡链路
- 或 D / 审校阶段的局部问题处理

### 1.4 执行层治理策略

不能只依赖 prompt。必须新增执行层 `globalConstraints` 审查器。

策略如下：

- 合法项：进入下游
- 非法项：拒收，不进入 B / 装配层 / D
- 拒收原因：显式写入 trace / readable artifact

注意：

- 不因单条非法约束直接卡死 A 阶段
- 不做静默吞掉
- 不把错误约束继续传播

### 1.5 与现有链路的兼容方式

- 保留现有 `globalConstraints` 字段和领域对象
- 保留现有 A prompt 和测试入口
- 新增的是“进入下游前的边界审查”，不是重写 A

## 二、C0 内生实体卡与 alias 归一机制

### 2.1 设计目标

在不重做 A/B 的前提下，为人物、地名、书名、关键术语建立项目级稳定锚点，补足当前“有传播、无归一、无实体锚点”的问题。

### 2.2 职责划分

- A：不负责 alias 归一主判断
- B：继续只提供弱信号
- C0：沉淀项目级内生实体卡，并在这里做证据驱动的 alias 归一
- 装配层：只筛选当前 chunk 可用卡
- D：消费卡，不从零裁决归一
- 后置审校 agent：做跨 chunk 收敛与裁决

### 2.3 B 侧信号保持不变

B 当前已有：

- `entities`
- `personAliasHints`
- `backgroundQuestions`
- `translationRisks`
- `keyExpressions`

这些能力全部保留。

它们在新设计中的定位是：

- 提供 alias / 命名治理弱信号
- 为 C0 的内生实体卡沉淀提供证据入口

### 2.4 C0 新增“内生实体卡”分支

现有 C0 外部知识检索与知识卡沉淀链路保留。

在此基础上新增一条“基于书内证据的内生实体卡”分支，用于处理：

- 虚构人物
- 虚构地点
- 书内别名
- 书内称呼变体
- 反复出现的重要术语与概念

这些内容不能依赖外部检索兜底，必须由 C0 基于书内证据沉淀。

### 2.5 人物卡最小结构

先做最小可用设计，不做巨型实体系统。人物卡至少应支持：

- `canonicalName`
- `aliasSet`
- `surfaceForms`
- `evidenceChunks`
- `firstSeenChunkId`
- `roleSummary`
- `confidence`
- `scope=PROJECT`
- 标注为“书内证据沉淀”，不是外部百科事实

对于地名、书名、关键术语，也应提供相同风格的内生实体卡，但字段可按类型微调。

### 2.6 alias 归一的核心原则

alias 归一不能做成“一次判定、直接固化”的静态策略。

必须支持以下演化状态：

- `observed`
- `suspected-alias`
- `confirmed-alias`

并允许后续发生：

- 候选升级为确认
- 确认降回候选
- 多张卡合并
- 一张卡拆分

### 2.7 merge / split 要求

知识卡归一结果必须可演化、可修正、可追溯。

因此：

- merge 不能静默发生
- split 不能静默发生
- 每次 merge / split 都要留下显式 trace
- 历史归一关系必须可回看

### 2.8 归一风格必须偏保守

默认策略应是：

- 宁可先保留多张卡 + 候选 alias
- 不要轻易强行并卡

因为小说场景里，误合并的代价远大于暂不合并。

所以：

- 高置信证据：可以 confirmed
- 中置信证据：先 suspected
- 低置信证据：只保留 observed，不做归一

### 2.9 哪些实体值得建卡

不做“每个实体强制一张卡”。

优先建卡对象：

- 多次出现的重要人物
- 存在 alias / 称呼漂移风险的人物
- 反复出现的重要地点
- 反复出现且影响一致性的书名、术语、核心概念

一次性路人或低价值实体，不强制建卡。

### 2.10 D 如何消费

D 继续保留现有：

- `confirmedTerms`
- `candidateTermUpdates`

同时增量接入相关内生实体卡。

D 消费时应区分：

- 已确认 alias
- 候选 alias
- 仅观察到的 surface form

人物卡不是绝对命令，而是带置信度的项目知识锚点。

## 三、链路内软约束与可修复式校验机制

### 3.1 设计目标

避免把主链做成“校验一紧就卡死”的机械流水线，而是逐步收敛为：

`生成 -> 显式发现问题 -> 定向修订 -> 少量高危阻断 -> 后置审校收敛`

### 3.2 问题分级

链路内问题统一分为三类：

#### `info`

只记录，不触发修订。

适用于：

- 低置信 alias 候选
- 弱 naming hint
- 暂不足以修正的轻微提示

#### `repair-required`

不中断链路，但必须进入下一轮修订或后置审校。

适用于：

- zh 目标下整句/整段法语残留
- 正文混入解释腔或知识卡泄漏
- glossary 未沿用
- 同 chunk 混用原文名和确认译名
- 首现命名不稳
- 显著别名漂移

#### `hard-fail`

只保留给极少数真正不能继续流转的情况。

适用于：

- 结构化输出损坏
- `translatedText` 基本为空
- 正文几乎未翻译
- 严重缺字段导致后续无法修订

### 3.3 D 的两轮机制保留，但角色调整

现有 D 两轮机制保留，不删除。

新的角色定义：

- 第 1 轮：产出可用草稿，并暴露问题
- 执行层检测：生成 issue 清单
- 第 2 轮：不是重翻，不是自由润色，而是“按 issue 清单定向修订”

### 3.4 D 侧新增的软约束检查

在现有正文边界污染检查之外，新增两类软约束：

#### 目标语言正文纯度

对 `zh` 目标语言，重点识别：

- 整句法语残留
- 整段法语残留
- 明显未翻译正文

允许豁免：

- 源文真实存在且必须保留的短引文
- 必要短专名
- 必要术语锚点

#### active glossary 正文合规

至少识别：

- 已确认术语未沿用
- 同一正文混用原文名和确认译名
- 明显命名漂移
- 首现命名没有沉淀为更新建议

### 3.5 默认处理方式

对上述问题默认使用 `repair-required`，而不是直接 hard fail。

只有在下列情况才升级：

- revision 后仍高置信整段法语残留
- 正文基本不可用
- 结构化结果已无法进入下一轮修订

### 3.6 与未来后置审校 agent 的衔接

未来自治审校/精修 agent 不负责基础清污。

它的职责应是：

- 跨 chunk 命名一致性审校
- alias 候选收敛与 merge / split 裁决
- unresolved issues 收敛
- 文风与忠实度精修

这要求主链先做到：

- 上游不再下发错误全局硬约束
- C0 提供稳定实体卡锚点
- D 能显式产出 issue，并完成 chunk 内可修问题的第一轮收敛

## 四、兼容接入策略

### 4.1 总原则

本次改造必须遵守：

- 只增不砍
- 先挂接、后替换
- 默认兼容现有链路

### 4.2 A 的兼容方式

- 保留当前 prompt 结构
- 保留 `globalConstraints` 字段
- 新增执行层边界治理

### 4.3 B 的兼容方式

- 保留当前 chunk 切分与标注职责
- 保留 `personAliasHints`
- 不把 B 扩成项目级实体治理器

### 4.4 C0 的兼容方式

- 保留现有外部知识检索与知识卡链路
- 新增内生实体卡分支
- 外部卡与内部卡共存，而不是互相替换

### 4.5 D 的兼容方式

- 保留现有两轮执行模式
- 保留当前 `confirmedTerms` 传播
- 保留当前正文边界 issue 检测
- 增量加入目标语言纯度与 glossary 合规 issue

### 4.6 后置审校 agent 的接入方式

- 作为新增后链，不侵入主链基础职责
- 主要消费：
  - 内生实体卡
  - active glossary
  - D 产生的 issue / unresolved notes

---

## 五、推荐实施顺序

推荐顺序如下：

1. 先做 A 的 `globalConstraints` 边界治理
2. 再做 C0 内生实体卡与 alias 归一链路
3. 再做 D 侧软约束 issue 与可修复式修订
4. 最后为后置自治审校 agent 设计稳定输入与接入点

原因：

- A 是当前最直接污染源，必须先切断
- C0 是后续命名治理和 alias 收敛的稳定锚点
- D 的软约束应建立在较干净的上游输入和较稳定的实体知识之上
- 后置 agent 不应在主链基础不稳时提前接管清污职责

---

## 六、需要持续坚持的原则

后续实现与审查必须始终检查以下几点：

- 不把 prompt 改动误写成链路已收稳
- 不把 B 的弱信号误升级为项目级事实
- 不把 C0 的候选 alias 误写成稳定事实
- 不把 D 的 repair-required 问题静默放过
- 不把未来后置审校 agent 变成主链基础清污工
- 不借设计之名顺手砍掉已有有效能力

本设计的核心目标不是把系统变成“更硬的流水线”，而是把它逐步收敛成“受控的可修复式流水线”。
